## 2. Findings

### SEC-001 — `dompurify@3.4.11` guards untrusted model output (HIGH)

| Field | Value |
|-------|-------|
| **severity** | HIGH *(advisory rates LOW; elevated on usage context)* |
| **category** | OWASP A06 — Vulnerable and Outdated Components / A03 — Injection |
| **file** | `apps/desktop/package.json:95`, `apps/desktop/src/components/assistant-ui/embeds/svg-embed.tsx:29` |
| **line** | 95 |
| **tool** | npm audit + manual correlation |

`dompurify` is pinned at exactly `3.4.11`, the top of the vulnerable range
(`<=3.4.11`), and it is a **production** dependency (`dev=false`), not dev tooling.

The advisory (`CUSTOM_ELEMENT_HANDLING` bypasses `afterSanitizeElements` for
allowed custom elements) is rated LOW in isolation. It is not low here, because
`svg-embed.tsx` uses DOMPurify as *the* security boundary between untrusted
LLM-generated SVG and an Electron renderer:

```tsx
DOMPurify.sanitize(code, { USE_PROFILES: { svg: true, svgFilters: true } })
// → dangerouslySetInnerHTML
```

The code comment states the intent plainly: *"so untrusted model output can't
execute."* A sanitizer bypass in a path whose entire job is sanitizing attacker-
influenceable content deserves prompt patching regardless of the CVSS label.

**Remediation:** `npm update dompurify` in `apps/desktop` to `>=3.4.12`. Non-breaking (patch).

### SEC-004 — `secrets: inherit` grants every sub-workflow the full secret set (MEDIUM)

| Field | Value |
|-------|-------|
| **severity** | MEDIUM |
| **category** | OWASP API5 — Broken Function Level Authorization / CI-CD-SEC-4 |
| **file** | `.github/workflows/ci.yml` |
| **line** | 77, 86, 93, 106, 113, 120, 126, 133, 140, 147, 168, 173 |
| **tool** | semgrep (`secrets-inherit`) |

Twelve `workflow_call` invocations pass `secrets: inherit`, handing each called
workflow every repository and organization secret rather than the specific ones
it needs.

**Mitigating factor:** `ci.yml` triggers on `pull_request` (not
`pull_request_target`), so **fork PRs receive no secrets at all** — GitHub
withholds them. Exposure is limited to same-repo branch PRs, where a contributor
with push access could add a step that exfiltrates any org secret.

**Remediation:** replace `secrets: inherit` with explicit `secrets:` blocks
listing only what each workflow consumes.

| **severity** | MEDIUM |

| **file** | `.github/workflows/js-tests.yml` |

| **tool** | checkov (CKV2_GHA_1) |

`js-tests.yml` sets no top-level `permissions`, so it inherits the caller's token
scope from `ci.yml` — which includes `packages: write`, `security-events: write`,
and `pull-requests: write`. A test workflow needs none of those.

**Remediation:** add `permissions: { contents: read }` at the top of `js-tests.yml`.

### SEC-006 — Deploy-hook secret passed inside a URL (MEDIUM)

| Field | Value |
|-------|-------|
| **severity** | MEDIUM |
| **category** | OWASP API2 — Broken Authentication ("no credentials in URLs") |
| **file** | `.github/workflows/deploy-site.yml` |
| **line** | 47 |
| **tool** | checkov (CKV_GHA_3) |

```yaml
run: curl -fsS --retry 3 --retry-delay 10 -X POST "${{ secrets.VERCEL_DEPLOY_HOOK }}"
```

The entire secret *is* the URL. Secrets in URLs land in shell traces, proxy logs,
and error output; `--retry` widens the window for a failure message to echo it.
GitHub masks known secret values in logs, which mitigates but does not eliminate
this (masking fails on partial/encoded forms).

**Remediation:** move it to `env:` and reference `"$DEPLOY_HOOK"`, so the value
never appears in the rendered command line.

### SEC-007 — `${{ }}` interpolated directly into `run:` blocks (LOW)

| Field | Value |
|-------|-------|
| **severity** | LOW (defense-in-depth) |
| **category** | OWASP A03 — Injection / CWE-78 |
| **file** | `.github/workflows/lint.yml:51`, `lockfile-diff.yml:50`, `tests.yml:44`, `e2e-desktop.yml:84`, `upload_to_pypi.yml:40` |
| **line** | 51 |
| **tool** | semgrep (`run-shell-injection`) |

`${{ github.base_ref }}` and `${{ inputs.slice_count }}` are expanded into shell
strings before the shell parses them.

**Not currently exploitable.** `github.base_ref` is the *target* branch (owned by
this repo, not the fork), and `slice_count` is hardcoded to `8` in `ci.yml`.
GitHub's own hardening guidance nonetheless says never to interpolate directly
into `run:`, because the safety here depends on a property of the *caller* that a
future refactor could silently break.

**Remediation:** pass through `env:` and reference `"$BASE_REF"`.

### SEC-009 — Messaging webhook adapters bind `0.0.0.0` by default (LOW / informational)

| Field | Value |
|-------|-------|
| **severity** | LOW |
| **category** | OWASP API8 — Security Misconfiguration |
| **file** | `gateway/platforms/msgraph_webhook.py:33`, `plugins/platforms/wecom/callback_adapter.py:54`, `gateway/platforms/whatsapp_cloud.py:89`, `plugins/platforms/teams/adapter.py:777`, `plugins/platforms/line/adapter.py:663`, `plugins/platforms/telegram/adapter.py:3716` |
| **line** | 33 |
| **tool** | bandit (B104) |

Six webhook receivers default to all-interfaces binding. This is inherent to
webhook receivers (the provider must reach them), and **signature verification was
confirmed present on every one checked**:

| Adapter | Authentication mechanism | Verified |
|---------|--------------------------|----------|
| MS Graph | `clientState` + `hmac.compare_digest` | ✅ `msgraph_webhook.py:274,349` |
| WhatsApp Cloud | `X-Hub-Signature` + `hmac.new` + `compare_digest` | ✅ `whatsapp_cloud.py:1417,1467,1509` |
| LINE | `hmac.new` + `compare_digest` | ✅ `line/adapter.py:268,276` |

| Teams | Bearer/JWT validation inside the Teams SDK (`_app.initialize()`) | ⚠️ delegated to SDK |

**Recommendation:** document that operators should firewall these ports and
terminate TLS at a reverse proxy. Consider making the bind host configurable with
a loopback default. Teams is the one worth an explicit confirmation that the SDK

## 10. Assessment

The security posture of this codebase is **strong**, and the evidence for that is
in the false positives rather than the findings. Repeatedly, the pattern a scanner
flagged turned out to be the mitigation:

- The `tarfile.extractall` hit was code that validates paths *and* uses `filter="data"`.
- The bidi-control-character hit was the sanitizer stripping them.
- The unverified-JWT hit was diagnostic-only code inside a failed-verification handler.
- The `dangerouslySetInnerHTML` hit was DOMPurify-guarded with the threat model in a comment.
- The `0.0.0.0` binds all had HMAC signature verification.
- The `USER root` finding ignored a documented `s6-setuidgid` privilege drop.

That level of "the control is already there, with a comment explaining why" is
uncommon. Combined with SHA-pinned actions, an existing OSV/supply-chain CI
pipeline, DNS-rebinding protection via Host-header validation in `web_server.py`,
and a fail-closed dangerous-command gate on `shell.exec`, this reads as a project
where security was designed in rather than bolted on.

The real work is routine dependency maintenance and tightening CI least-privilege.
